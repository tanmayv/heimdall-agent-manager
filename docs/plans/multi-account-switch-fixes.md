# Multi-Account Switch Fixes (Message Send & API Errors)

Status: Proposed. RCA validated against `main` @ `2843ae32`.
Builds on: `docs/plans/multi-account-switcher.md` (v0.5.55).

## 1. Problem

After adding several accounts and switching between them, users see failed message sends and 403/404 API errors in both the webapp and Electron. The RCA from `task_18e917b7e7760fae` was checked line by line. The table shows the verified causes in priority order.

| ID | Verdict | Root cause | Evidence |
|---|---|---|---|
| RC-1 | **CONFIRMED (primary)** | Account A's vault keyring gets installed during account B's session. `runRefresh` stops checking `stale()` after `deviceVault.ts:428`. It awaits `publishChain` (`:429`), then calls `installKeyringFromWrap(A.identity, …)` (`:479-482`) and dispatches `ready` (`:485`) after `enterSwitching → stopDeviceVault` has already purged the keys. The guard in `vaultKeyringSession.ts:50,61` captures the generation after the purge, so it does not catch this. `publishChain` (`:203-206`) also reads the global `ctx` after an await, so it can write A's head-freshness record and fingerprint into B's state. B's messages are then encrypted under A's vault ID: B's bridges reject them (`unseal_protocol.odin:768`) and the UI shows "From a previous vault". ## 2. Requirements

- **`REQ-SWFIX-VAULT-1` (refresh fencing)**: every `await` in `runRefresh` is followed by `if (stale()) return;`, including after `publishChain` and immediately before every `installKeyringFromWrap`, `setActiveVaultKey` and status `dispatch`. `publishChain` uses the `c` passed in, never the global `ctx`. `installKeyringFromWrap` takes the expected keyring generation as a parameter, captured when the refresh starts, and refuses to install when it has changed. `bootDeviceVault` bumps the keyring generation whenever the user changes.
- **`REQ-SWFIX-VAULT-2` (foreign keyring purge)**: whenever a refresh for user B takes the `pending`, `revoked`, `hub_unreachable` or `register` path, any installed keyring whose `userId !== c.userId` is purged before that path's status is dispatched.
- **`REQ-SWFIX-VAULT-3` (background task cancellation)**: a module `vaultGeneration` is incremented by `stopDeviceVault`. `stopDeviceVault` also clears `hintTimer` and resets `autoUnsealRunning`. `autoUnsealLockedBridges`, `scheduleHintRevocation` callbacks and `fetchVerifiedChain` capture `const c = ctx` (or the generation) up front, use `c.userId`, and abort when `ctx !== c`. No TypeError is thrown when `ctx` becomes null mid-flight.
- **`REQ-SWFIX-VAULT-4` (idempotent boot)**: `bootDeviceVault(userId)` with `ctx?.userId === userId` never rebuilds `ctx`. It returns `refreshDeviceVault('boot')`.
- **`REQ-SWFIX-SEND-1` (send guard)**: `sendConversationMessage` and `answerConversationQuestions` refuse to send when an active vault key exists whose `userId` is not the current authenticated user. If encryption is expected for this account (the vault is enrolled or approved but not yet `ready`, for example `initializing` after a switch), the send is blocked with a visible "Vault unlocking…" state rather than sent as plain text. The `AgentChatPane` composer shows the blocked or disabled state and keeps the draft text.
- **`REQ-SWFIX-STALE-1` (stale context detection)**: the client sends `X-Heimdall-Expected-User: <user_id>` on every authenticated API request, and as a WS-upgrade query param or header where headers are not possible. When the active session's user differs, the hub responds `409 account_mismatch` (JSON error code `account_mismatch`). Requests without the header behave as before, which keeps CLI/MCP/bridge clients working. The UI fetch observer treats `account_mismatch` like `heimdall:api-unauthenticated`, and the stale context resyncs right away. The user WebSocket is closed or re-validated when its user is no longer the active account for that browser. At minimum, the client closes it on `account_mismatch`.
- **`REQ-SWFIX-IDENT-1` (identity refresh)**: when `refreshIdentity` finds the same user still authenticated, it keeps the existing `auth` object reference (updating it only if fields differ) and skips `boot()`. User actions (`switchAccount`, `signOutAccount`, `addAccount`) are never dropped silently: they pre-empt or wait for an in-flight background refresh, for example by bumping `generation`. 401/403 events that arrive during a refresh are queued, not dropped.
- **`REQ-SWFIX-ROUTE-1` (route isolation)**: `resolveSwitchedUserRoute` returns `'#/home'` when the target user has no saved route. An optional small allowlist of account-neutral routes (`#/home`, `#/settings/*` minus account-specific pages) is acceptable. `addAccount` calls `saveRoute(authRef.current)` and builds `return_to` with hash `#/home`. `saveRoute` never persists `#/device/enroll`.
- **`REQ-SWFIX-ELECTRON-1`**: after the OIDC return, `openOidcWindow.finishIfReturned` forces a full document reload of the main window, for example `main.webContents.reload()` when the URL differs only by hash, or `loadURL` followed by `reload()`. Closing the login window without a return clears the add-account intent in the main renderer (via IPC or an equivalent mechanism).
- **`REQ-SWFIX-MCP-1` (minor)**: the MCP worker unregister (`setMcpWorkerEnabled(false)`) is awaited, with a short timeout, before `POST /api/v1/auth/switch` is sent, so it cannot land as the new account.

## 3. Out of scope

- Changing the session ring or cookie format, or revoking deselected sessions on switch.
- Multi-account support for CLI/MCP clients.

## 4. Verification expectations (worker chooses exact commands)

- Unit tests:
  - RC-1 race: a refresh for A suspended in `publishChain`, then `stopDeviceVault` and boot for B. A's keyring is never installed, and status never becomes `ready` for A's data.
  - Send guard: a foreign `userId` key blocks the send, and a not-ready vault blocks plain-text fallback.
  - `resolveSwitchedUserRoute` table cases.
  - Same-user `refreshIdentity` keeps the object reference and does not reboot the vault.
  - `stopDeviceVault` clears timers.
- Hub test: an expected-user mismatch returns 409 `account_mismatch`, and a missing header is unchanged.
- Typecheck plus the existing multi-account, sidebar, settings and handoff suites still pass.
- `npm run build:electron` passes.
- A manual or e2e note for the two-tab scenario: switch in tab 1, send from tab 2. Expected result: tab 2 resyncs and the message goes out as the correct user.
