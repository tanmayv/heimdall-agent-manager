# Phase 0 credential vault and browser conventions

**Review target.** An owner saves a credential in Settings, copies its opaque reference into a task, and an agent on an approved, unlocked bridge can use that reference through a bounded local operation. An agent can also reuse a browser login established on that bridge. The browser profile and credential store have independent lifetimes.

## REQ-VLT-0 · Owner workflow and trust boundary

Add a Secrets panel to Settings, alongside the existing Devices panel. Keep device enrollment and recovery in Devices. Wire direct navigation and reopening through `src/ui/components/settings/SettingsModal.tsx`, `src/ui/utils/settingsRouting.ts` and `src/ui/components/shell/AppShell.tsx` (`resolveSettingsTab`, `DeviceVaultGate`). Show a masked value input, name, and, for the first supported consumer, the intended HTTPS endpoint. A plain stored secret may omit the endpoint and is then ineligible for agent use. Generate a cryptographically random 128-bit ID before sealing. Allow duplicate names. Copy reference copies only the ID. Edit loads one record on demand. Cancel, lock, logout, reset and unmount clear component state. Keep plaintext out of Redux, query keys, persistent caches, analytics and error reports. Guard async completions with the session generation to avoid redisplaying data after lock or account change.

The existing design in `docs/plans/passwordless-vault.md` uses an owner directory and epoch keys. `src/hub/repository/sqlite/vault_directory_repo_sqlite.odin` stores the directory behind `src/hub/repository/iface/vault_directory_repo.odin`. `src/ui/utils/vaultKeyringSession.ts` installs a verified device wrap with `installKeyringFromWrap` and drops the session with `clearKeyringSession`. `src/ui/utils/vaultKeyring.ts` imports owner-bound bytes and selects keys with `currentKey` and `keyFor`. Use the current epoch for every new write and the specified historical epoch for reads. Refuse writes under stale vault ID/epoch, checking current directory state in the mutation transaction. Namespace queries by current vault ID so reset immediately isolates old records; retire obsolete rows in bounded background batches by old namespace. Rotation retains access to older ciphertext on still-approved devices. Revocation cannot erase previously learned values or invalidate third-party sessions.

Seal name and secret payload separately to list names without moving values. Use the authenticated-context pattern of `sealFsWriteContent` and `openFsWriteContent` in `src/ui/utils/vaultCrypto.ts`. Define an interoperable length-prefixed UTF-8 context containing protocol version, owner, vault ID, epoch, ID, record revision and field tag. Use fresh random nonces for both fields and re-seal both on every edit. Secret payload includes consumer kind, exact destination and value. Verify context on opening. Generic text decryption must fail. Lock and unknown epoch fail closed. Publish deterministic TS/Odin vectors using test-only fixed nonces. Hub validates full envelope syntax, encoded bounds, declared epoch and vault ID. Only key holders can verify authenticated plaintext. Hub observes IDs, sizes, revisions and access patterns.

### Store and API

Add an additive migration under `src/hub/repository/sqlite/migrations/` following `src/hub/repository/sqlite/migrations.odin`. Proposed table `credential_secrets(owner_id,vault_id,id,revision,name_ct,payload_ct)`, all fields required, composite primary key on the first three columns, WITHOUT ROWID. Validate canonical lower-case hex IDs, positive integral revisions, overflow, strict request fields and total body size before decoding. Cap clear name at 256 UTF-8 bytes, value at 16 KiB and URL at 2 KiB. Bound armored fields at 1 KiB and 32 KiB respectively and body at 40 KiB. Serialize the inner payload with a bounded binary length-prefix format so JSON escaping cannot inflate it past the envelope limit.

| Operation | Database and wire contract |
|---|---|
| List | Select ID, revision and name ciphertext only. Equality on owner and vault, ordered by ID. For subsequent pages add `id > ?`. Bind limit 1–50 (default 25) plus one to determine continuation. Cursor is last returned ID. Live keyset traversal permits concurrent inserts behind the cursor to appear on refresh. |
| Read | Equality on all three primary-key columns. Single detail record. A bridge-only read returns only revision and sealed payload. |
| Create | Insert at revision 1. Unique conflict returns 409. After ambiguous transport failure, read the same ID and compare exact submitted ciphertext before declaring success. |
| Edit/delete | Single conditional UPDATE or DELETE with full primary key and expected revision. Edit increments exactly once. On zero affected, owner-local point lookup in the same transaction distinguishes stale (409) and missing (404). A foreign ID gives the same missing result. Refetch on conflict and let the owner reapply. Delete retry treats absence as achieved. |

Never accept owner from body, cursor or query. For UI routes use authenticated user and approved device signature, covering method, full target including cursor, and exact body, with replay protection. Follow `require_vault_user`, `signed_request` in `src/hub/transport/http/vault_directory_handlers.odin` and `verify_request(.Approved)` in `src/hub/service/vault_directory/service.odin`. Restrict writes and detail/list to those routes. Give bridge fetch a distinct read-by-ID route requiring an active bridge credential, matching enrolled owner and approved bridge device, checked on every fetch. Derive bridge identity from authentication as in `src/hub/transport/http/agent_handlers.odin` (`require_auth_or_bridge_token` requires an additional bridge-kind check here). Deny enrollment, user-only bearer, arbitrary instance bearer and revoked bridges at this route. Return Cache-Control no-store. Publish only owner-scoped invalidation and ID following successful commit.

## REQ-SKILL-0 · First supported consumer

Proposed `ham-ctl secrets check --id <id>` performs an authenticated HTTPS GET against the exact owner-configured read-only endpoint. Example: an owner configures a token and their service’s authenticated account-status URL, then asks the agent to check connectivity with the copied ID. The agent receives success, authentication rejected, or unavailable. This first operation verifies the credential with its intended service. Additional provider-specific actions need their own reviewed consumers.

The instance shim sends only the ID to its local bridge endpoint. Validate the running instance token and its bridge binding. The bridge obtains ciphertext over its own authenticated connection, opens the dedicated context with its live keyring and sends an Authorization bearer header directly to the fixed destination. Accept only well-formed HTTPS URLs with host and validated certificates, no userinfo, fragments or header control bytes; disable redirects, ambient proxies, retries, cookie jars, request tracing and response-body logging. Bound time, response headers and connections; discard body without rendering. Reject agent-supplied destinations, headers, commands or operation templates. Release buffers promptly and wipe owned mutable secret buffers on all exits. Redact transport exceptions by mapping to fixed result codes. Avoid argv, environment, temp files and general-purpose child processes. The endpoint operator necessarily receives the credential.

`src/bridge/vault_decrypt.odin` has lock/reset, historical epoch open and keyring wipe paths. Implement a context-specific opener alongside them. `src/ctl/vault_content.odin` has `ctl_vault_open` and generic `ctl_decrypt_json_value`; keep the credential response out of both generic output and fallback rendering. `bridge_prespawn_env` documents live key access via `agent.vault.get`. Same-account processes, other tools and a compromised bridge are trusted in this phase. A skill can instruct agents to use the narrow command and report only status. It cannot constrain arbitrary shell, memory inspection, the remote service or externally supplied scripts. Never paste the value into a prompt to recover from failure. Lock means ask the owner to unlock; a missing reference means ask for the ID.

## REQ-BRW-0 · Persistent bridge-local browser login

Resolve one absolute `HEIMDALL_BROWSER_PROFILE_DIR` from the bridge’s persistent per-registration data directory, outside instance run directories and worktrees. Create it for the service account with owner-only directory access or equivalent Windows ACL. Reject symlink traversal or unsafe ownership. Use the same value across restarts and agents on this registration, distinct paths across registrations. Add it to `bridge_prespawn_env` in `src/bridge/bootstrap_prespawn.odin` and propagate through `src/bridge/acp_runtime.odin`, `src/bridge/hub_runtime_client.odin` and the shell execution path in `src/bridge/bridge_shell_session.odin`; verify from the actual child in each supported mode. The path contains no key. Browser data contains live sessions. Keep it out of artifacts, backups shared with agents and transcripts.

Operator opens an existing compatible browser using its persistent-profile option, signs in interactively and closes it. Later agents use the same profile with that browser family. Use headed mode when a usable graphical session exists. Without a display, use supported headless persistent mode for already-authenticated work or return display-required for interactive login. Never launch a disposable fallback profile silently. Serialize participating launches using a bridge-local OS lock for the profile lifetime and honor the browser’s own profile lock, including externally launched browsers. Return busy promptly; never remove a live lock, clone cookies or attach to an unrelated running browser. Same bridge agents share account-level access. Browser logout or owner cleanup revokes local reuse independently of vault lock. Phase 0 requires neither package installation nor a debugging port.

## REQ-FUT-0 · Later boundaries

A later policy layer can authorize an operation on a secret for a specified owner, bridge and agent until an absolute expiry; evaluate it at use time with revocation and trusted time. It needs independent design for existing general-purpose key access. No counts, grant records, cards, renewal or permission workflow ship in this slice. A future desktop service can identify an OS window and mediate capture and input with platform consent, focus and lifetime checks independently of browser vendor or debugging protocol. Streaming, remote input and capture are deferred.
