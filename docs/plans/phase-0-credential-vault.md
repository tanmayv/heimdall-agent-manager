# One-time secure agent forms

An operator can give a waiting agent’s trusted local script several inputs in one explicit submission. Only the script receives the values. The agent sees a fixed outcome. This revision replaces the stored-credential plan at 224c26fc. Keep the held branches intact. The independent browser-profile work can proceed separately. The approved flow is [One-time secret request](artifact://art_18ebb60116c1c1fe).

## Repository boundaries

The current grouped form in `src/ui/components/chat/MultiQuestionForm.tsx` offers familiar field layout and an explicit submit. Its failed-request draft and chat answer flow are unsuitable here. In `src/hub/transport/http/multi_question_handlers.odin`, the handler calls `content_service.answer_questions`, which constructs a Chat_Message. The SQLite repository in `src/hub/repository/sqlite/multi_question.odin` implements fresh-answer insertion, and the handler calls `publish_user_message_created` after insertion. A secure form must split before all three operations. Render pending forms in a separate authenticated conversation panel. Refresh its metadata on open, reconnect and a metadata-only invalidation. Chat insertion order has no authority over a secure request.

Use agent-mode dispatch in `src/ctl/agent_mode.odin`, the authenticated local wrapper boundary in `src/bridge/wrapper_endpoint.odin`, the Bridge runtime client in `src/bridge/hub_runtime_client.odin` and the existing authenticated live Bridge connection. The proxy relay in `src/hub/transport/http/bridge_proxy_relay.odin` illustrates connection routing. Introduce dedicated bounded frames. Do not tunnel via shell sessions, chat, proxy uploads, offline commands, job queues or a keyring-unseal payload.

## Request and protocol

Proposed interface: `ham-ctl secure-form run --form form.json --script /absolute/path --timeout 180 --execution-timeout 60`. The version-1 public form has a purpose and an ordered array of 1–12 required fields with unique ASCII IDs, plain labels and types text, password, single or multiple. Choices carry unique IDs and labels. Disallow defaults, freeform markup, unexpected keys and duplicate JSON members. Limit public schema to 32 KiB, encoded plaintext to 32 KiB and envelope to 64 KiB. Validate UTF-8, required nonempty values, choice membership and multiple-choice uniqueness in both endpoints. Treat every submitted field as confidential. Labels, purpose and choices are public routing/display data and must contain no secrets.

1. The local wrapper authenticates the instance and derives owner, bridge and conversation from runtime placement. Reject caller overrides. Resolve and pin the owner-controlled trusted script before registration. Allocate a random 256-bit request ID, monotonic deadline, fresh ECDH keypair and in-memory waiter. Sign the immutable descriptor below. Register over the authenticated Bridge channel. Hub verifies peer placement and bounds, indexes only non-secret metadata in RAM and acknowledges registration immediately. Idempotent registration requires identical descriptor and live connection generation. Suppress form display until registration succeeds.
2. The CLI waits locally using an immediate local start response and bounded short status polls authenticated to that invocation. Neither a Hub RPC nor a local endpoint worker waits for the operator. CLI interruption explicitly cancels. A local waiter heartbeat and deadline reclaim orphaned requests. Do not place local invocation capabilities in public metadata.
3. The UI fetches pending descriptors using an owner-authenticated same-origin endpoint. Show verified requester, bridge, script identity, purpose, labels and deadline. Hold inputs only in component memory. Disable password saving/autocomplete where supported. Clear fields on navigation, lock, decline, expiry and send attempt. Prevent double click, page restore and client retries. Use no-store responses and exclude bodies from service workers, telemetry, diagnostics and network-error snapshots.
4. On explicit submit the UI signs and encrypts locally. A dedicated authenticated POST validates origin/CSRF, ownership, envelope size, live generation and deadline. Under a per-request lock reserve the first submission, then attempt one nonblocking bounded send on that exact connection. Return immediately with metadata status. No payload in storage, event bus, dead letters, access logs, debug traces or metrics. Release frame memory after write/drop. Only status notifications may fan out. Client may refresh status after lost HTTP response. Never resend the body.
5. Bridge validates the envelope against its own descriptor and active owner device trust, then under its waiter lock checks local monotonic deadline, cancellation, invocation liveness and pending state again. Atomically consume the waiter and detach the private key before acknowledging acceptance or scheduling the script. Readers and WS writers must never wait for a human or subprocess. One bounded execution worker owns the plaintext and the sole launch right. Zero mutable buffers and discard keys on every exit. Managed browser strings and OS copies have best-effort lifetimes.

## Cryptographic binding

Reuse the verified directory trust decision in `src/ui/utils/vaultBridgeDelivery.ts` and `vaultDirectoryVerify.ts` and signature primitives used by `vaultBridgeUnseal.ts`. Require the chain-approved Bridge identity and a currently authorized owner device signing key. Fail closed on locked, missing, stale or revoked trust. Bridge verifies the device against its trusted owner directory state and refuses when freshness cannot be established. TLS and the Hub login restrict routing. The signed descriptor and response protect against relabeling and key substitution by a relay. Trusted UI distribution, device and Bridge host are assumptions.

Use a versioned binary transcript with each component prefixed by a four-byte big-endian byte length. Encode strings as UTF-8, timestamps as canonical unsigned decimal Unix milliseconds and public keys as raw uncompressed P-256 points. Bridge identity signs the domain string heimdall.secure-form.request.v1 followed by owner, bridge, connection generation, instance, conversation, request ID, deadline, script display name and pinned content SHA-256, SHA-256 of the exact UTF-8 public form bytes, and recipient public key. Transport the exact schema bytes and render only the verified parse. Browser verifies all displayed context against the signed bytes and current conversation. Device generates a fresh P-256 ECDH sender key, derives 32 bytes using HKDF-SHA256 over the shared secret with transcript SHA-256 salt and heimdall.secure-form.answer.v1 info. AES-256-GCM uses a random 12-byte nonce, full 128-bit tag and transcript digest as AAD. Device signs a separately domain-prefixed length-framed tuple of transcript digest, device ID, sender key, nonce and ciphertext including tag. Bridge verifies signature, digest and key encodings before decrypting and validates the exact ID-to-value map. Freeze positive and negative byte vectors across Odin and WebCrypto before dependent implementation.

## Delivery and execution outcomes

Hub admission is pending → forwarding → accepted → final. Bridge ownership is pending → consumed → running → final. Decline (authenticated owner), cancel (originating invocation), local expiry and verified acceptance compete for one transition out of pending. A decline racing a forwarded frame can claim success only after Bridge confirms it won. After consumption a cancel cannot promise prevention. Kill an active process group if requested and report uncertain effects. Reject expired UI submissions server-side even when the tab clock lags. Reconnection creates a new generation. Never attach old requests to it. Hub restart loses routing state, Bridge restart loses waiters. Bound status tombstones to the request deadline plus a short grace period. Unknown or missing status after forwarding never authorizes another attempt.

| Exit | Fixed meaning |
|---|---|
| 0 | Script reported success |
| 20 | Invalid or unauthorized request |
| 21 | Owner declined before consumption |
| 22 | Response deadline expired before consumption |
| 23 | Cancelled before consumption |
| 24 | Delivery failed with positive evidence no acceptance occurred, including offline before send |
| 25 | Script could not start or failed to receive complete stdin |
| 26 | Script exited unsuccessfully |
| 27 | Execution deadline expired |
| 28 | Delivery or execution outcome unknown |

A dropped acknowledgement after a possible send, process failure after consumption, or lost local completion maps to 28 unless authoritative Bridge status resolves it. Disclose that codes 25–28 can follow external side effects. Require a new explicit operator request after checking the external result. A partial stdin write cannot justify rerunning the script. Reject malformed/duplicate frames without disturbing a valid consumed request. Separate execution deadline starts at consumption.

Use a dedicated local noninteractive runner with verified immutable script bytes (open and verify ownership, mode, symlink policy and digest, execute the same pinned content). Give the trusted Bash process a single bounded versioned JSON document on a private anonymous stdin pipe, close after complete write, and map exit/timeout to fixed codes. Disable tracing, startup files, core dumps and inherited descriptors, use a minimal reviewed environment and null stdout/stderr before spawn. Never interpolate answers into commands, arguments, environment, files or captured output. Use a process group and reap on deadline. Scripts can read and disclose their input, make network requests and cause irreversible effects. The owner must trust the script, its dependencies and destination.

## Agent-only browser sign-in

Tools inherit the absolute `HEIMDALL_BROWSER_PROFILE_DIR` under the configured data root for this Bridge registration. Keep the native exclusive profile lock, same browser family, OS identity and cookie key store across runs. Report busy or unavailable and preserve the profile. Use an already-installed browser with a private automation pipe. A trusted controller owns one browser and tab throughout. Verify relying-party origin and intended account first. Reuse an authorized session if present. Otherwise request username/password or a later one-time code via the secure form for the current verified provider step. A trusted stdin consumer passes values only to the same controller via an owner-only local pipe bound to a one-use step nonce. Verify top-level origin, frame, target document and destination immediately before input and submit. Abort on navigation or mismatch. Disable password saving, tracing, screenshots and sensitive output. The profile intentionally retains session cookies. For account choice or consent ask explicitly with nonsecret labels. On passkey, CAPTCHA, denied consent or an unsupported challenge, stop with the actual outcome. Verify the intended account back at the relying party before reporting success.
