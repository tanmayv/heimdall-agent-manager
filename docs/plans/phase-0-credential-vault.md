# One-time secure agent forms

An operator can give a waiting agent’s trusted local script several inputs in one explicit submission. Only the script receives the values. The agent sees a fixed outcome. This revision replaces the stored-credential plan at 224c26fc. Keep the held branches intact. The independent browser-profile work can proceed separately. The approved flow is [One-time secret request](artifact://art_18ebb60116c1c1fe).

## Repository boundaries

The current grouped form in `src/ui/components/chat/MultiQuestionForm.tsx` offers familiar field layout and an explicit submit. Its failed-request draft and chat answer flow are unsuitable here. In `src/hub/transport/http/multi_question_handlers.odin`, the handler calls `content_service.answer_questions`, which constructs a Chat_Message. The SQLite repository in `src/hub/repository/sqlite/multi_question.odin` implements fresh-answer insertion, and the handler calls `publish_user_message_created` after insertion. A secure form must split before all three operations. Render pending forms in a separate authenticated conversation panel. Refresh its metadata on open, reconnect and a metadata-only invalidation. Chat insertion order has no authority over a secure request.

Use agent-mode dispatch in `src/ctl/agent_mode.odin`, the authenticated local wrapper boundary in `src/bridge/wrapper_endpoint.odin`, the Bridge runtime client in `src/bridge/hub_runtime_client.odin` and the existing authenticated live Bridge connection. The proxy relay in `src/hub/transport/http/bridge_proxy_relay.odin` illustrates connection routing. Introduce dedicated bounded frames. Do not tunnel via shell sessions, chat, proxy uploads, offline commands, job queues or a keyring-unseal payload.

## Script admission

Provision an administrator-managed manifest outside the agent's write authority. Require OS-enforced separation for the manifest, interpreter, script, dependencies, controller binary and their parent directories. Each entry pins their canonical paths and content digests, the allowed destination, purpose and expected controller identity. The agent's script argument selects an existing entry. Reject agent-created programs, mutable imports, writable search paths, an unverified controller peer or any digest mismatch before displaying a form. Revalidate and execute pinned bytes on each attempt. Bind the manifest entry digest into the signed descriptor and display its verified purpose, script identity and approved destination. A same-UID agent with debugging, process-injection or pipe-impersonation access could still obtain the values. The deployment must isolate agent processes from the Bridge, runner and controller with distinct principals or an enforced sandbox and authenticated IPC. Disable secure forms if this boundary cannot be established. The browser skill must document that prerequisite and residual host-administrator and trusted-script access.

### Linux provisioning and registration predicate

Ship an opt-in Linux deployment with a dedicated unprivileged Bridge service account and an isolated agent host under a second unprivileged account. The existing same-UID deployment continues to run ordinary jobs. An administrator provisions the service accounts, private data directories and system services. A new agent-host process owns **all** untrusted execution for that registration (ACP, TUI, managed shells, tool commands and their descendants). The privileged side of this trust boundary runs only the trusted Bridge service and admitted runners/controllers. Disable any generic command, shell, proxy or file interface that could operate on the trusted host as its UID. Keep provider credentials, working directories and ordinary agent browser state on the agent side. The trusted controller alone owns the persistent authenticated browser profile for secure sign-in. An agent requiring that session requests operations from that controller. Sharing its files or unrestricted automation socket with the agent defeats isolation.

At startup require Linux peer credentials on a connected Unix socket to the provisioned agent host, a root-owned service configuration specifying distinct nonzero numeric UIDs/GIDs, and a matching Bridge effective UID/GID. Both installed units drop all capabilities, enforce NoNewPrivileges and exclude the other service's private directories. Admit only instances actually spawned by this agent host after authenticated registration. Each invocation uses its Bridge-issued instance credential plus matching agent-host SO_PEERCRED UID/GID. Accept controller IPC only over an inherited socketpair to the pinned child with its launch nonce and verified process identity; check credentials on a child-originated message using SCM_CREDENTIALS (PID, UID, GID). Reject existing same-UID children, missing identity, inactive split deployment, credential mismatches or an alternate local shell route. Probe page locking and dump exclusion for the maximum secret allocation before advertising the form, return 24 on failure and repeat the checks at allocation. Linux is the first supported target; other platforms require a separately verified equivalent.

Install the manifest at `/etc/heimdall/secure-forms/manifest.json` through an explicit administrator deployment step. Require root UID, regular file, mode 0644 or 0600 readable by the trusted service, and root-owned parent directories with no group/other write. Resolve by directory handles without symlink traversal. The Hub and agent have no provisioning operation. Version 1 is an object with exactly `version` (integer 1) and `entries` (array). Each entry has exactly the string keys `id`, `purpose`, `destination`, `script`, `interpreter`, `controller` and the array `files`. Use unique ASCII IDs, an HTTPS origin in canonical browser origin serialization, absolute canonical paths, and an empty controller string for non-browser jobs. Each file record contains exactly `path` and lowercase 64-hex `sha256`. Require each executable and dependency in files; reject duplicate paths, unknown members and mutable dependencies. Resolve --script by unique exact canonical script path. Hash the length-framed UTF-8 components in this order: domain heimdall.secure-form.manifest.v1, id, purpose, destination, script, interpreter, controller, decimal file count, then path and sha256 for every record sorted by UTF-8 path bytes. Send this public entry for UI recomputation. For general scripts destination is the administrator's attestation. For browser scripts the controller additionally enforces origin on every sensitive operation.

## Request and protocol

Proposed interface: `ham-ctl secure-form run --form form.json --script /absolute/path --timeout 180 --execution-timeout 60`. The version-1 public form requires a plain-text, single-sentence purpose describing the intended use (1–200 characters, one line), an optional logo from a bundled first-party asset ID allowlist, and an ordered array of 1–12 required fields with unique ASCII IDs, plain labels and types text, password, single or multiple. Choices carry unique IDs and labels. Disallow defaults, freeform markup, unexpected keys and duplicate JSON members. Limit public schema to 32 KiB, encoded plaintext to 32 KiB and envelope to 64 KiB. Validate UTF-8, required nonempty values, choice membership and multiple-choice uniqueness in both endpoints. Treat every submitted field as confidential. Labels, purpose and choices are public routing/display data and must contain no secrets.

1. The local wrapper authenticates the instance and derives owner, bridge and conversation from runtime placement. Reject caller overrides. Resolve and pin the owner-controlled trusted script before registration. Allocate a random 256-bit request ID, monotonic deadline, fresh ECDH keypair and in-memory waiter. Sign the immutable descriptor below. Register over the authenticated Bridge channel. Hub verifies peer placement and bounds, indexes only non-secret metadata in RAM and acknowledges registration immediately. Idempotent registration requires identical descriptor and live connection generation. Suppress form display until registration succeeds.
2. The CLI waits locally using an immediate local start response and bounded short status polls authenticated to that invocation. Neither a Hub RPC nor a local endpoint worker waits for the operator. CLI interruption explicitly cancels. A local waiter heartbeat and deadline reclaim orphaned requests. Do not place local invocation capabilities in public metadata.
3. The UI fetches pending descriptors using an owner-authenticated same-origin endpoint. Show verified requester, bridge, script identity, purpose, labels and deadline. Render the logo only for a recognized bundled ID; omit it when absent and reject URLs or inline markup. Immediately above Submit display “Your browser encrypts these values for the named script. Heimdall does not save them to persistent storage. The Bridge keeps them in memory for up to five minutes. During that time this agent can explicitly retry the same script for this task without asking you again.” Hold inputs only in component memory. Disable password saving/autocomplete where supported. Clear fields on navigation, lock, decline, expiry and send attempt. Prevent double click, page restore and client retries. Use no-store responses and exclude bodies from service workers, telemetry, diagnostics and network-error snapshots.
4. On explicit submit the UI signs and encrypts locally. A dedicated authenticated POST validates origin/CSRF, ownership, envelope size, live generation and deadline. Under a per-request lock reserve the first submission, then attempt one nonblocking bounded send on that exact connection. Return immediately with metadata status. No payload in storage, event bus, dead letters, access logs, debug traces or metrics. Release frame memory after write/drop. Only status notifications may fan out. Client may refresh status after lost HTTP response. Never resend the body.
5. Bridge validates the envelope against its own descriptor and active owner device trust, then under its waiter lock checks local monotonic deadline, cancellation, invocation liveness and pending state again. Atomically consume the waiter and detach the private key before acknowledging acceptance or scheduling the script. Readers and WS writers must never wait for a human or subprocess. One bounded execution worker owns the plaintext and the sole launch right for that attempt. Zero mutable buffers and discard keys on every exit. Managed browser strings and OS copies have best-effort lifetimes.

## Five-minute retention and explicit retries

Record the Bridge's monotonic receipt time when the complete live answer frame arrives, before validation or worker scheduling. Only a successfully authenticated first submission establishes a retained entry. Its immutable expiry is receipt time plus 300 seconds, including time spent validating and waiting for a worker. Use an elapsed-time clock that includes suspend, or invalidate entries on resume. Allocate dedicated non-dumpable, page-locked storage before decrypting (Linux MADV_DONTDUMP and mlock, or platform equivalents such as VirtualLock plus crash-dump exclusion). Scrub before unlock and release. If protections cannot be established, refuse secret delivery with code 24 before consumption. Keep the accepted values exclusively in private Bridge process memory between attempts. Scrub transient worker copies after each stdin write. Discard the retained entry on expiry, explicit cancellation, instance teardown or Bridge restart. Drop malformed and duplicate frames immediately. Reads, successful use, failed use, reconnects and retry attempts never renew the deadline.

The form deadline governs submission. The retention deadline governs further access to accepted values. The execution deadline bounds each child. Once a script receives input it controls its own copies. Expiry closes outstanding Bridge writes, clears the retained buffer and prevents further delivery. It cannot revoke bytes already delivered. Synchronize the expiry timer, worker access, cancellation and input writes. Recheck expiry before launch and each nonblocking write so delayed cleanup cannot extend access.

### Explicit local retries

The initial owner submission authorizes the named script and purpose, including explicit retries by the same agent instance on the same bound task during the original retention window. Explain this before submission. The agent can invoke `ham-ctl secure-form retry --request <id> --after-attempt <n>` after a failed attempt. Both commands print the nonsecret request and attempt IDs and poll a local waiter for fixed status. Authenticate the local caller anew and derive its owner, bridge, instance and task from verified placement. Match all four and the original manifest, script digest and purpose; reject mismatches with 20. Check external effects before retrying an uncertain result. Require a confirmed terminal prior attempt; unresolved status returns 28. A retry is a deliberate local command. No second owner prompt, approval challenge, Hub answer frame or automatic replay occurs.

Under one lock, compare the supplied prior attempt to the latest terminal attempt and check the immutable retention deadline. Issue its successor once. Concurrent or repeated commands naming that same predecessor join the existing successor or return its status. An explicit subsequent command must name a newly failed predecessor. Reconnection on the same Bridge preserves local retention; Bridge restart, discard or expiry returns 29 and requires a fresh submission. Keep nonsecret attempt status until the metadata deadline.

## Cryptographic binding

Reuse the verified directory trust decision in `src/ui/utils/vaultBridgeDelivery.ts` and `vaultDirectoryVerify.ts` and signature primitives used by `vaultBridgeUnseal.ts`. Require the chain-approved Bridge identity and a currently authorized owner device signing key. Fail closed on locked, missing, stale or revoked trust. Bridge verifies the device against its trusted owner directory state and refuses when freshness cannot be established. TLS and the Hub login restrict routing. The signed descriptor and response protect against relabeling and key substitution by a relay. Trusted UI distribution, device and Bridge host are assumptions.

Carry the signed directory proof as a separate bounded attachment (256 KiB maximum, independently of the 64 KiB answer envelope) on initial answer submissions. Bind its sequence and head hash in the device signature. Follow `src/bridge/mcp_transform.odin` at registration and on each decision: require unlocked `bridge_read_vault_keyring`, found `keystore_read_epoch_floor`, a set root pin and passing `epoch_floor_check`. Follow `src/lib/vault/control_job.odin` and `src/lib/vault/directory_verify.odin`: match owner, vault, epoch and signed directory head and sequence, run `directory_verify` and `directory_verify_keyring`, reconstruct and compare the pinned root, and require both target Bridge and signer in the verified trusted map. Require signer approval_seq at or before signed sequence and kind_policy.can_approve. Reject rollback below the highest locally verified sequence for this vault and forks at the same sequence; serialize verification and monotonic checkpoint advancement across decisions. This enforces locally observed revocations; a withholding relay can conceal newer directory updates. Locked keyring, absent pin, unpaired Bridge or unauthorized proof returns 20 without launch.

For v1 form signatures use ECDSA P-256/SHA-256, fixed 64-byte unsigned big-endian r||s on the wire. Convert DER only at a library boundary, reject malformed or out-of-range scalars and reject unsupported signing-key algorithms. Preserve the repository's native verification formats for existing directory entries.

Use a versioned binary transcript with each component prefixed by a four-byte big-endian byte length. Encode strings as UTF-8, timestamps as canonical unsigned decimal Unix milliseconds and public keys as raw uncompressed P-256 points. Bridge identity signs the domain string heimdall.secure-form.request.v1 followed by owner, bridge, connection generation, instance, task ID, conversation, request ID, deadline, manifest entry digest, verified destination, script display name and pinned content SHA-256, SHA-256 of the exact UTF-8 public form bytes, and recipient public key. Transport the exact schema bytes and render only the verified parse. Browser verifies all displayed context against the signed bytes and current conversation. Device generates a fresh P-256 ECDH sender key, derives 32 bytes using HKDF-SHA256 over the shared secret with transcript SHA-256 salt and heimdall.secure-form.answer.v1 info. AES-256-GCM uses a random 12-byte nonce, full 128-bit tag and transcript digest as AAD. Device signs a separately domain-prefixed length-framed tuple of transcript digest, device ID, directory sequence and head hash, sender key, nonce and ciphertext including tag. Bridge verifies signature, digest and key encodings before decrypting and validates the exact ID-to-value map. Freeze positive and negative byte vectors across Odin and WebCrypto before dependent implementation.

## Delivery and execution outcomes

Hub admission is pending → forwarding → accepted → final. Bridge ownership is pending → consumed → running → final. Decline (authenticated owner), cancel (originating invocation), local expiry and verified acceptance compete for one transition out of pending. A decline racing a forwarded frame can claim success only after Bridge confirms it won. After consumption a cancel cannot promise prevention. Kill an active process group if requested and report uncertain effects. Reject expired UI submissions server-side even when the tab clock lags. Reconnection creates a new generation. Never attach old requests to it. Hub restart loses routing state, Bridge restart loses waiters. Keep Hub and Bridge routing status and duplicate-rejection tombstones through max(form deadline, retention expiry + maximum execution timeout) + 60 seconds. Before receipt is known use form deadline + 300 seconds as the upper bound for retention expiry. Keep metadata only; this grace period never extends access to values. Unknown or missing status after forwarding never authorizes another attempt.

| Exit | Fixed meaning |
|---|---|
| 0 | Script reported success |
| 20 | Invalid or unauthorized request |
| 21 | Owner declined before consumption |
| 22 | Initial response deadline expired before consumption |
| 23 | Cancelled before consumption |
| 24 | Delivery failed with positive evidence no acceptance occurred, including offline before send |
| 25 | Script could not start or failed to receive complete stdin |
| 26 | Script exited unsuccessfully |
| 27 | Execution deadline expired |
| 28 | Delivery or execution outcome unknown |
| 29 | Retained inputs expired or were discarded; fresh form required |

Once dispatch recognizes secure-form, malformed flags and schema, wrong principal, locked keyring and missing pairing map to 20. If the local wrapper cannot be reached before any request was sent, return 24. Losing the wrapper or Bridge mid-wait after possible submission returns 28 unless authoritative status resolves it. Generic ham-ctl startup or dispatch failures before secure-form handling retain existing codes 1/2; neither proves a script ran. Never propagate a child's numeric exit directly.

A dropped acknowledgement after a possible send, process failure after consumption, or lost local completion maps to 28 unless authoritative Bridge status resolves it. Disclose that codes 25–28 can follow external side effects. Require an explicit local retry command after checking the external result. A partial stdin write cannot justify rerunning the script. Reject malformed/duplicate frames without disturbing a valid consumed request. Separate execution deadline starts at consumption.

Use a dedicated local noninteractive runner with verified immutable script bytes (open and verify ownership, mode, symlink policy and digest, execute the same pinned content). Give the trusted Bash process a single bounded versioned JSON document on a private anonymous stdin pipe, close after complete write, and map exit/timeout to fixed codes. Disable tracing, startup files, core dumps and inherited descriptors, use a minimal reviewed environment and null stdout/stderr before spawn. Never interpolate answers into commands, arguments, environment, files or captured output. Use a process group and reap on deadline. Scripts can read and disclose their input, make network requests and cause irreversible effects. The owner must trust the script, its dependencies and destination.

## Agent-only browser sign-in

Tools inherit the absolute `HEIMDALL_BROWSER_PROFILE_DIR` under the configured data root for this Bridge registration. Keep the native exclusive profile lock, same browser family, OS identity and cookie key store across runs. Report busy or unavailable and preserve the profile. Use an already-installed browser with a private automation pipe. A trusted controller owns one browser and tab throughout. Verify relying-party origin and intended account first. Reuse an authorized session if present. Otherwise request username/password or a later one-time code via the secure form for the current verified provider step. A trusted stdin consumer passes values only to the same controller via an owner-only local pipe bound to a one-use step nonce. Verify top-level origin, frame, target document and destination immediately before input and submit. Abort on navigation or mismatch. Disable password saving, tracing, screenshots and sensitive output. The profile intentionally retains session cookies. For account choice or consent ask explicitly with nonsecret labels. On passkey, CAPTCHA, denied consent or an unsupported challenge, stop with the actual outcome. Verify the intended account back at the relying party before reporting success.
