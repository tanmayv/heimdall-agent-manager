# Bridge-owned runtime and local search

The authenticated Bridge that creates a chain permanently owns its complete task runtime in local SQLite. The Hub keeps only vault-protected chain titles/descriptions and task titles, access and routing metadata. Detail requests pass through the Hub to that Bridge. Decrypted content and full-text search stay local. If the owner is unavailable, mutations and fresh detail reads wait; another copy never becomes the owner.

**Status:** proposed plan for task `task_18e554dbf43e7642`, requirements revision **5**. Independent review and explicit final-plan user approval precede implementation. Browser caching is a separate follow-up. Full encrypted Hub read caches, materialized read snapshots, delta subscriptions, ownership transfer, automatic failover and consensus are outside this implementation.

**Amendment (2026-11-07):** by user decision the Bridge-owned runtime has no task attempt budget. Owner-local grants do not count attempts or refuse work for budget exhaustion/oscillation, and there is no `budget.activate`; owner-local migration V29 drops the budget tables and releases tasks the budget overlay blocked. Attempt numbers remain archival identity, `brief.budget.hard_deadline` still sets the lease hard deadline, and the Hub taskv2 budget is unchanged. Budget mentions below describe the original Hub only.

## 2. Immutable owner, creation and recovery (REQ-LOCAL-1)

**Creation:** CLI issued on Bridge A uses A's enrolled signing identity. A browser must explicitly choose an enrolled online creator Bridge; its signed create request is delivered there. The owner is the authenticated recipient that commits creation, never a client-supplied arbitrary `bridge_id`, worker placement or coordinator's later device. Owner and user/device signatures bind account, new chain ID, creation operation ID, owner Bridge key and schema version. Bridge-local commit creates the chain, initial ACL, receipt and registry-publication intent atomically. The Hub registers this signed genesis once; a conflicting genesis/owner is rejected, and lost responses replay the same operation. Chain existence does not depend on successful metadata publication: until publication succeeds it is locally committed, publication pending.

**Authentication:** keep account/device enrollment and vault pairing; extend contracts with signed, domain-separated command envelopes rather than treating a content key or claimed Bridge ID as authority. The existing proof verifier authenticates signed enrollment chains (`src/lib/vault/bridge_chain.odin:16-60,248-328`), but is not yet a task-command protocol. A human device signs commands with its approved device key. The owner grants scoped capabilities to agents, bound to exact instance launch/token generation; execution Bridges attest local token validation. Owner verifies both capability and executor signature. Hub checks account access before relaying; owner repeats authorization against local grants. No Hub-invented `user approved` command is accepted.

**Legacy chains:** require explicit owner selection by the account user, never “first reconnect wins.” Freeze that chain's Hub mutations, drain/reconcile live leases and pending merges/stops, export one consistent aggregate plus a row-count/hash manifest, import into the selected Bridge in one transaction, verify counts/events/facets and register signed genesis/import receipt. Only then disable old Hub write routes and publish owner routing. All IDs and historical authors survive. Failure before activation leaves the old authority frozen or explicitly resumed; after activation rollback must first stop/drain the local writer. Never keep two writable stores. Chains with unresolved executions cannot be imported as idle.

**Restart:** one OS-held exclusive writer lock per account/profile database, SQLite WAL with `synchronous=FULL`, foreign keys and migrations before serving. An unchanged durable database restarts under the same Bridge identity; increment its persisted runtime incarnation and reconcile outbox/reservations/children before new grants. Owner identity never changes. Runtime incarnation fences obsolete processes; it is not an ownership epoch or takeover mechanism. Persist wall-clock high watermark and clock generation; uncertain/backward clocks block timed mutations until reconciled. Reconstruct deadlines without extending hard caps.

**Offline:** if the owner process/device is unavailable, no other Bridge or Hub grants, renews, submits, reviews or edits. Executors may perform already-authorized bounded computation and safety stops, but cannot fabricate task commits. Reconnect first reconciles expiry/cancellation and exact child state. If only the Hub is down, authenticated owner-local operations may continue against cached grants until their authorization expiry; remote operations wait. Lost replies are unknown outcomes, retried with the same operation ID.

**Restore/loss:** backups are consistent encrypted snapshots with signed manifest `(account, owner_bridge, database_id, schema, commit_seq, content hashes, created_at, key_id)`. Restore only to the same enrolled owner identity after proving the previous writer and affected executor children are stopped. A stale backup or disk clone cannot safely resume active authority merely by incrementing a local number. Require comparison with retained signed executor/client receipts and a clean drained checkpoint; otherwise remain recovery-required. No automatic disk-loss failover. Acknowledged commits after the latest complete backup can be permanently lost; show the precise backup sequence/recovery point. Lost identity keys or inability to prove fencing means archive/read recovery only, or a separately approved new chain with new identity. Copies confer neither write permission nor new owner status.

### Atomic rule and command ordering

For every mutation request (including retries): bound and parse the envelope, authenticate identity/signature and immutable owner/account binding, and verify current read authorization for the operation's result scope (independent of a released mutation lease). Open the local UoW, recheck that authorization, then look up `(principal_id, operation_id)` **before live mutation admission**. Verify the stored method/input digest against the canonical signed input. A matching receipt returns only its historical result, marked as replay rather than current authority, without changing state or creating/reissuing effects. Changed input conflicts. Only a receipt miss may proceed through request-expiry, current mutation grant, clock, exact live fence and expected-revision checks; then apply state/events/facets/source changes, insert receipt/change entries/durable intents, commit and perform I/O. A rejected candidate rolls back its nested savepoint including receipts, facets and intents. Disk-full or commit failure produces no success response. There is no network call while holding the UoW.

Envelope fields: `protocol_version, account_id, chain_id, immutable_owner_bridge, principal_id, operation_id, method, expected_revision, request_expires_ms, exact_fence?, payload_digest, key_id, signature`; canonical body is encrypted end to end through Hub. Reject duplicate/unknown raw fields and mismatched signatures/digests. Within one owner, SQLite serializes accepted operations and assigns commit sequence. Dependent commands name expected revision/fence; a batch is bounded and explicitly atomic or explicitly per-item, never implicit partial success.

Same principal/operation/input returns the stored historical result after current read authorization **even when the original request has expired or its mutation lease/fence has been released, retired or expired**. This is read-only replay; it bypasses live mutation admission, never renews a grant and never authorizes a launch. Changed-input conflict detection also precedes live admission. An expired receipt miss is rejected, and an operation tombstone is rejected as retired (changed digest conflicts), never treated as a new command. Executor must separately validate current fence/deadline before acting on any grant evidence. New command envelopes expire within five minutes; receipts remain for at least 30 days and until all related active intents/executions settle. Compact old ones into durable expired-operation tombstones retaining principal/operation/method/input digest. Bound receipts/tombstones and changes with per-account quotas (initially 100,000 receipts/tombstones and 1,000,000 change entries); reject admission with a visible retention-capacity error rather than discard active replay evidence. Archive/drain and explicitly close old command-grant generations before reclaiming their tombstones. Auth/key rotation retains required verification material; revocation can suppress replay bodies while preserving deduplication. Pending-card source episodes cannot be pruned as merely resolved.

### Remote executor reservations

Each execution Bridge owns a device-wide SQLite reservation ledger shared by **all** chain owners and manual agent launches. Exact slot selection is done there, never from a stale Hub count. Proposed records:

```sql
CREATE TABLE executor_slots (
  slot_id TEXT PRIMARY KEY, account_id TEXT NOT NULL,
  policy_revision INTEGER NOT NULL, provider_profile TEXT NOT NULL,
  enabled INTEGER NOT NULL CHECK(enabled IN (0,1))
);
CREATE TABLE executor_reservations (
  reservation_id TEXT PRIMARY KEY, operation_id TEXT NOT NULL UNIQUE,
  input_digest TEXT NOT NULL, owner_bridge TEXT NOT NULL, chain_id TEXT NOT NULL,
  slot_id TEXT NOT NULL REFERENCES executor_slots(slot_id),
  instance_id TEXT NOT NULL, directory_key TEXT NOT NULL,
  configuration_revision INTEGER NOT NULL, launch_epoch TEXT NOT NULL,
  run_count INTEGER NOT NULL, grant_generation INTEGER NOT NULL,
  state TEXT NOT NULL CHECK(state IN ('prepared','active','stopping','released')),
  prepare_until_ms INTEGER NOT NULL, hard_ms INTEGER NOT NULL,
  executor_incarnation INTEGER NOT NULL, result_json TEXT NOT NULL
);
CREATE UNIQUE INDEX slot_live ON executor_reservations(slot_id)
  WHERE state != 'released';
CREATE UNIQUE INDEX instance_live ON executor_reservations(instance_id)
  WHERE state != 'released';
CREATE UNIQUE INDEX directory_live ON executor_reservations(directory_key)
  WHERE state != 'released' AND directory_key != '';
```

Directory key is the canonical protected worktree/root resource, not an unchecked caller path. Slots are a configured finite pool under device/account/provider budgets; budgets are static signed allocations per execution Bridge, so sum cannot exceed the account entitlement. No opportunistic global quota borrowing. Reallocation drains old reservations before installing replacement budget. A warm process counts until stopped; fleet capacity is additionally checked at the owner. Manual launches use the same slot ledger. Different owner databases therefore cannot double-book a device or instance.

Protocol: owner persists prepare intent → executor atomically reserves exact slot/instance/configuration and returns signed reservation → owner revalidates and commits grant plus activate intent → executor atomically validates reservation, owner proof and fence, persists child launch intent and launches once. Duplicate prepare/activate/query returns same record; changed payload rejects. Expired prepared reservation cannot activate, even if owner committed too late: owner retires that failed grant through a recovery event without charging an agent failure. Lost replies query the same reservation. Active/stopping reservations remain charged until exact-child stop/exit proof; timeout alone cannot free a running process. Executor crash reconciles children before offering slots. Process fences include Bridge identity, executor incarnation, instance, launch epoch/run count, configuration/token generation, reservation, lease and grant generation; PID alone is insufficient. Stop targets the old fence and cannot hit a newer child.

This initial scope has no detail-delta replay protocol. Cancel requests accepted by the owner are distinct from physical stop confirmation. In-flight plaintext results are discarded on account switch, logout, vault lock or grant revocation; prevent late responses entering another account's store. Persistent browser plaintext/encrypted caching remains deferred, requiring its own opt-in/privacy/revocation design.

## 5. Durable decrypted local SQLite FTS (REQ-LOCAL-4)

User authorization permits plaintext **on the enrolled Bridge**, not on the Hub. Store the runtime DB and FTS on an account-private encrypted OS volume (directory `0700`, files `0600`, equivalent Windows user ACLs). SQLite itself is not assumed encrypted. Initial setup checks the configured private storage location and makes the at-rest boundary explicit; backups are separately encrypted. The service account/OS administrator can read decrypted files while the volume is unlocked; vault lock cannot retroactively erase them. Keep canonical vault envelopes for transport/backup and explicit local plaintext search documents. Avoid a new database encryption framework in this task.

Use a durable `search_docs` plus FTS5 in the **same database** as canonical local objects:

```sql
CREATE TABLE search_docs (
  rowid INTEGER PRIMARY KEY, account_id TEXT NOT NULL,
  chain_id TEXT NOT NULL, task_id TEXT NOT NULL DEFAULT '',
  object_kind TEXT NOT NULL, object_id TEXT NOT NULL,
  object_revision INTEGER NOT NULL, visibility_scope TEXT NOT NULL,
  title TEXT NOT NULL, body TEXT NOT NULL,
  UNIQUE(account_id, object_kind, object_id)
);
CREATE VIRTUAL TABLE search_fts USING fts5(
  title, body, content='search_docs', content_rowid='rowid', tokenize='unicode61'
);
```

Index chain/task titles and descriptions, goals/acceptance, task comments, linked conversation messages, handoff/output prose and textual artifact content. Skip credentials, auth tokens, private keys, raw binary artifacts and terminal transcripts by default. Types without an approved extractor remain fetchable but unindexed, visibly documented. Imported non-chain content requires an explicit scope grant and producer version; never crawl arbitrary filesystem paths.

Reuse the INSERT/UPDATE/DELETE external-content trigger sequence at `src/bridge/task_chain_search_index.odin:108-125`, adapted to `search_docs(title,body)`: DELETE postings use **old** values, then UPDATE inserts new values. Source mutation, decrypted doc upsert/delete and commit sequence are one transaction; key/decryption failure aborts a content write rather than silently claiming indexed success. For an existing encrypted import while locked, persist ciphertext plus pending-index marker, return `search_not_ready` for that scope and rebuild after unlock. Reindex into a transaction or shadow index and swap only at the captured vault/database generation; concurrent lock/revocation invalidates work. The existing generation test is `src/bridge/task_chain_search_index_test.odin:142-151`.

Query uses bound parameters, literal token escaping from `src/bridge/task_chain_search_index.odin:221-244`, bounded execution time and 100-hit/256-KiB limits. Join local grant-derived allowed chain/object scope **before** ranking, count and snippet extraction; user-provided filter IDs are intersections, never authority. Recheck ACL revision before returning. Results carry object revision and indexed sequence; snippets never enter logs, metrics or Hub indexes. Search RPCs reuse sealed request/response transport (`src/bridge/task_chain_search_rpc.odin:89-144`) but must add principal/scoped authorization rather than relying on shared vault-key possession. Device-signed command authority and content decryption keys are separate.

Vault/key lifecycle: store account keyring and owner signing keys in existing OS keystore/pairing flow, not SQLite. Lock closes search handles, clears plaintext memory/queued results, increments generation and denies search/content mutations until unlocked. Durable plaintext remains protected by OS volume/ACLs; offer explicit purge of the local search index. Rotating vault content keys rewraps/reindexes as required, retaining old keys only for authorized history/backup recovery. Revoking a device removes its routing/grants and denies new requests once observed; disconnected devices cannot be remotely forced to forget previously decrypted content. Short-lived grants bound this delay; no claim of instant offline revocation.

Recovery: integrity-check DB and FTS, rebuild from authorized canonical rows using FTS `rebuild`; do not raw-delete an external-content index. Existing repair warnings explain this constraint (`src/hub/repository/sqlite/fts_repair.odin:9-21,46-80,98-104`). A failed FTS repair marks search unavailable without turning any copy into authority. Backup through SQLite's consistent backup interface, include referenced blobs, seal archive before copying to explicitly configured backup storage, verify manifest/hash and restore in isolation before activation. Initial scope does not store full backup/read-view blobs on the Hub. Exclude derived plaintext FTS from portable backups where possible; rebuild after authorized restore. OS snapshots that include plaintext need the same encrypted-volume/access policy.

Deletion: transactionally delete canonical object/its search doc/postings, create minimal version tombstone and registry-delete intent; cascade/GC referenced blobs after readers release them. Revoke applicable local copies/grants. Checkpoint/truncate WAL and perform secure-delete/compaction maintenance with bounded downtime; old FTS segments, filesystem snapshots, SSD behavior and existing backups prevent a promise of forensic erasure. Track every backup/copy deletion acknowledgement; apply deletion tombstones before exposing restored data. Expire old backups under declared retention, destroy expired backup keys and tell the user when offline copies have not acknowledged deletion. A copy is not a read fallback until separately authorized; it is never a writer.
