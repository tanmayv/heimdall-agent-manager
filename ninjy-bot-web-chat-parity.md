The web chat can reuse the coordinator’s tool and action components once the bot transcript supplies their inputs. Read receipts can use the existing bot refresh event after the bot commits a read. ## REQ-CHAT-2 · Read receipts before replies

`src/bridge/wrapper_endpoint.odin:573` records a successful channel-read relay on the bridge. The authoritative read boundary is `src/hub/transport/http/bot_agent_handlers.odin:55`, which selects a binding via `src/hub/service/bots/routing.odin:52` and calls `src/hub/service/bots/feedback.odin:20`. Under the service mutex, this selects a bounded batch, tracks newly read rows, and commits exactly the selected inbound IDs. `src/hub/repository/sqlite/bot_repo_sqlite.odin:1164` sets the first `read_at` in a transaction. Pending means unanswered (`bot_repo_sqlite.odin:647`), so repeated reads may still return the same rows while preserving their original timestamps. Reply accounting is separate (`bot_agent_handlers.odin:95` and `bot_repo_sqlite.odin:1440`).

Publish the existing owner-scoped `bot_changed` event from `bots_channel_read` once after a successful commit with newly read rows. Publish outside the service mutex and before adapter feedback so slow provider calls cannot delay browser visibility. `src/hub/service/bots/pairing.odin:55` supplies the publisher and `src/ui/api/wsInvalidation.ts:1260` already invalidates the Bot cache. The history API returns `read_at` (`bot_web_handlers.odin:82`), which `botChatModel.ts:166` and `:202` render independently of `replied_at`. Apply the refresh to loaded older pages as well as the head, using the existing cursor cache or a bounded refresh of the pages the user has loaded. Keep the read state monotonic across delayed fetches. On an attachment lookup failure after commit, the receipt follows the committed read and the retry can return the same pending messages. Leave provider feedback and reply routing on their existing paths.

## Server contract for live tools and interactive actions

The revised REQ-CHAT-1 keeps tool activity live and persists interactive action references. `GET /api/v1/bots/me` returns the current bot instance and its conversation as `advanced.agent_instance_id` and `advanced.conversation_id`. The instance must belong to both the caller and the bot’s durable agent. Subscribe using the existing instance-scoped tool stream. That stream checks viewer ownership and accepts producer frames for the instance’s current Bridge connection and run only. The unified owner chat sees the bot runtime’s live activity across delivery channels. A frame does not identify an individual Telegram, WhatsApp, or web turn, and tool activity is transient.

The bot can send a web text reply with `ham-ctl channel send --text "Please review" --action crd_…`. Use repeated `--action` or comma-separated `--actions` for multiple cards. The agent send API accepts `params.action_ids` with up to 16 distinct existing card IDs owned by the bot owner. Normal reply routing picks the binding. An action-bearing message is rejected if that binding is Telegram or WhatsApp, or if the send contains an artifact. A split text reply carries references on its last chunk.

`GET /api/v1/bots/me/messages` returns `metadata: { action_ids: string[] }` on the outbound web row when it has visible references. The existing message ID and cursor remain stable. The card API supplies current details and status. History omits deleted or inaccessible references, and retention clears the stored references along with the body.
